 try {

3. Critical Assessment (No Diplomacy)
What is genuinely better now?
1. Concurrency and Data Integrity: The modern way is atomic. In the 2025 code, if two requests hit /checkout at the same time, both read the identical inventory.json file before either writes it back (a classic Time-of-Check to Time-of-Use race condition). The second write silently overwrites the first, corrupting the sold counters and overselling physical food. A database transaction eliminates this by design.
2. Non-Blocking Event Loop: The old way uses fs.readFileSync and fs.writeFileSync. These freeze the entire Node.js single thread for every other connected user while Node waits on Windows disk I/O. As orders.json grows, serializing megabytes of stringified JSON synchronously on every purchase will stall the API.
3. Partial Failure Recovery: If writeOrdersSafe() succeeds but the process crashes before writeInventorySafe() completes, the system enters a split-brain state where orders exist for food that the database never marked as sold. In a transactional model, failures automatically roll back completely.
What did the old way do better?
1. Zero Operational Overhead: There are no migrations, no database engines to install, no schema files to compile, and no Docker daemons to manage.
2. Trivial Debuggability: You can open orders.json in Notepad or VS Code, inspect the raw data, manually edit an order, and save it. For an undergraduate class demonstration lasting 5 minutes, this eliminates 90% of local setup headaches.
3. No Dependency Bloat: The old way uses only built-in Node standard library modules (fs, path). Prisma pulls in native C++ engine binaries (@prisma/engines), adds over 50MB to node_modules, and frequently breaks cross-platform compilation between macOS, Windows, and Linux CI environments.
